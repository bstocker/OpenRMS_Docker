--------------------------------------------------------------------------------
2. POURQUOI LE DIAGNOSTIC EST TROMPEUR
--------------------------------------------------------------------------------
Trois fausses pistes classiques sur ce probleme :

a) "C'est localhost / le port forwarding Codespaces."
   NON. Le port 80 publie fonctionne : nginx recoit bien les requetes, elles
   apparaissent dans ses logs d'acces. Le trafic local hote -> conteneur passe
   par la chaine OUTPUT, PAS par la chaine FORWARD, donc il n'est pas filtre.
   Seuls les sauts DERRIERE nginx echouent.

b) "C'est le DNS Docker."
   NON. La resolution interne est correcte :
       getent hosts frontend backend
       172.18.0.4  frontend
       172.18.0.3  backend
   Les noms resolvent, c'est la connexion TCP qui echoue. D'ou l'apparence
   d'un bug applicatif OpenMRS.

c) "C'est OpenMRS / la configuration de la distro."
   NON. Aucun fichier du depot n'est en cause. Le probleme est au niveau du
   pare-feu du noyau de la machine hote.


--------------------------------------------------------------------------------
3. CAUSE RACINE
--------------------------------------------------------------------------------
Deux backends netfilter sont actifs SIMULTANEMENT sur la machine :

  * iptables-nft  : utilise par Docker 29.7
                    (/etc/alternatives/iptables -> /usr/sbin/iptables-nft)
                    Docker y installe correctement ses chaines :
                      -A DOCKER-FORWARD -i br-92f4e92bd07b -j ACCEPT
                    => la table nft AUTORISE le trafic.

  * iptables-legacy : table orpheline pre-remplie par l'image de base du
                      Codespace, heritee d'une ancienne version de Docker :
                        -P FORWARD DROP
                        -A FORWARD -i docker0 ! -o docker0 -j ACCEPT
                        -A FORWARD -i docker0 -o docker0 -j ACCEPT
                      => aucune regle pour le bridge de la composition,
                         et la politique par defaut est DROP.

Un paquet doit etre accepte par LES DEUX backends pour passer. Le trafic
conteneur -> conteneur sur le bridge de compose (br-92f4e92bd07b) est donc
jete par la table legacy, bien que la table nft l'autorise.

Consequence en chaine :
   gateway -> frontend  : bloque  => nginx timeout => HTTP 504
   backend -> db        : bloque  => wait-for-it.sh tourne dans le vide
                                  => backend jamais (healthy)

Indice a ne pas ignorer : toute commande iptables affiche l'avertissement
   "Warning: iptables-legacy tables present, use iptables-legacy to see them"

--------------------------------------------------------------------------------
5. CORRECTIF APPLIQUE
--------------------------------------------------------------------------------
Remede habituellement conseille sur le web (NON retenu ici) :
    sudo iptables-legacy -P FORWARD ACCEPT
  -> Efficace, mais desactive le filtrage de TOUT le trafic transite de la
     machine. Trop large : rejete lors de cette intervention.

Correctif retenu : trois regles ACCEPT ciblees sur le SEUL bridge du projet,
la politique globale DROP restant intacte.

    BR=br-92f4e92bd07b   # a adapter : voir section 4, commande 4

    sudo iptables-legacy -I FORWARD 1 -i $BR -o $BR -j ACCEPT
    sudo iptables-legacy -I FORWARD 2 -i $BR ! -o $BR -j ACCEPT
    sudo iptables-legacy -I FORWARD 3 -o $BR \
         -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT

Resultat (la politique reste DROP, seul ce bridge est autorise) :
    -P FORWARD DROP
    -A FORWARD -i br-92f4e92bd07b -o br-92f4e92bd07b -j ACCEPT
    -A FORWARD -i br-92f4e92bd07b ! -o br-92f4e92bd07b -j ACCEPT
    -A FORWARD -o br-92f4e92bd07b -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT
    -A FORWARD -j DOCKER-USER
    -A FORWARD -j DOCKER-ISOLATION-STAGE-1
    ...

Aucun redemarrage de conteneur n'a ete necessaire : le backend, qui bouclait
sur wait-for-it.sh, a joint la base des l'application des regles.

--------------------------------------------------------------------------------
7. LIMITE IMPORTANTE : LE CORRECTIF N'EST PAS PERSISTANT
--------------------------------------------------------------------------------
Les regles visent un NOM D'INTERFACE (br-92f4e92bd07b), lui-meme derive de
l'ID du reseau Docker. Elles sont donc perdues, et le 504 revient, apres :

  - un "docker compose down" (le reseau est supprime puis recree avec un
    nouvel ID, donc un nouveau nom de bridge) ;
  - un redemarrage / une reconstruction du Codespace (table legacy remise a
    zero par l'image de base).

Un simple "docker compose restart" ou "stop/start" ne detruit pas le reseau :
les regles survivent.

Deux facons de rendre la solution durable :

  Option A - Figer le nom du bridge dans la composition (fichier suivi par git)
      networks:
        default:
          driver_opts:
            com.docker.network.bridge.name: openmrs-br0
      Les regles peuvent alors viser "openmrs-br0" de facon permanente.
      Inconvenient : modifie un fichier du depot pour un contournement propre
      a l'environnement Codespaces.

  Option B - Script de post-demarrage hors depot (recommande)
      Detecter le bridge puis reappliquer les regles, par exemple via
      postStartCommand dans .devcontainer, ou a la main apres chaque
      "compose up". Le nom du bridge se recupere ainsi :
        NETID=$(docker network inspect -f '{{.Id}}' \
                openmrs-distro-referenceapplication_default)
        BR="br-${NETID:0:12}"

11. CAUSE : DEUX PHASES DISTINCTES, A NE PAS CONFONDRE
--------------------------------------------------------------------------------
PHASE A - Assistant "initialsetup" bloque (a necessite un redemarrage)
  Le webapp a demarre AVANT que le fichier de proprietes runtime existe :
      WARN OpenmrsUtil.getRuntimeProperties - Unable to find a runtime
           properties file. Initial setup is needed.
  OpenMRS a donc installe son InitializationFilter, puis l'auto-setup
  (install_method=auto) a execute les migrations Liquibase et ecrit
  /openmrs/data/openmrs-runtime.properties. Mais le filtre ne peut pas rendre
  la main sans redemarrage, d'ou :
      java.lang.IllegalStateException: Filters cannot be added to context
      [/openmrs] as the context has been initialised
  Consequence : /openmrs/ws/rest/v1/session renvoyait HTTP 302 vers
  /openmrs/initialsetup au lieu du JSON attendu.
  NOTE : cette course a ete provoquee par le blocage reseau de la partie 1,
  qui a fait patienter le backend ~12 min sur wait-for-it.sh.

  Correctif : docker compose restart backend
  (Les regles iptables-legacy de la partie 1 SURVIVENT a un restart : le
  reseau n'est pas recree. Verifie apres coup.)

PHASE B - Generation des donnees de demo saturant le CPU (a juste demande du temps)
  Apres le redemarrage, le port 8080 acceptait le TCP mais AUCUNE requete ne
  recevait de reponse (HTTP 000 apres 180 s).
  Element decisif du thread dump : ZERO thread "http-nio".
  Le socket etait bien binde (les connexions s'empilaient dans la file
  d'attente du noyau) mais aucun worker n'existait encore : Tomcat n'avait pas
  fini de deployer openmrs.war. Confirmation dans les logs : "Done refreshing
  Context" present, mais aucun "Server startup" apres le redemarrage.

  Le thread responsable, identifie par le dump (611 s de CPU sur 1065 s) :
      "pool-4-thread-1" ... runnable
        org.openmrs.module.referencedemodata.orders.DemoOrderGenerator
          .createDemoTestOrder(DemoOrderGenerator.java:57)
        -> OrderServiceImpl.saveOrder
        -> OrderServiceImpl.getActiveOrders
        -> HibernateOrderDAO.getActiveOrders
        -> SessionImpl.autoFlushIfRequired
        -> AbstractFlushingEventListener.postFlush
        -> StatefulPersistenceContext.forEachCollectionEntry
  Le module referencedemodata genere les donnees de demo
  (global_property referencedemodata.createDemoPatientsOnNextStartup = 50).
  Chaque commande sauvegardee declenche un auto-flush Hibernate qui reparcourt
  tout le contexte de persistance : cout quadratique. Sur 2 vCPU dont un
  sature (+ pression GC : G1 Conc#0 a 170 s de CPU), l'operation est tres longue.

POURQUOI L'ECRAN EST GRIS PLUTOT QU'UNE ERREUR :
  Les fichiers statiques du SPA sont servis par le conteneur "frontend"
  (nginx), independant du backend. Ils repondent donc HTTP 200 et la coquille
  de l'application se charge normalement. Mais tous les appels API vers le
  backend restent suspendus => aucun composant ne peut s'initialiser => gris.

 'for p in $(ls /proc | grep -E "^[0-9]+$"); do
    exe=$(readlink /proc/$p/exe 2>/dev/null);
    case "$exe" in *bin/java) jcmd $p Thread.print > /tmp/td.txt 2>&1; break;; esac;

# Puis extraire sa pile
docker compose exec -T backend sh -c 'awk "/^\"pool-4-thread-1\"/,/^\$/" /tmp/td.txt'
